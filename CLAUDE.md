# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Rangiffler — QA.GURU Advanced diploma scaffold: a travel photo app (map of visited countries, photo feed, likes, friends). The goal is to turn the monolithic `rfr-api` into microservices (gRPC suggested for inter-service calls) and to build a substantial e2e/API test suite in `rfr-e2e`. READMEs (root and per module) are in Russian and are the authoritative design notes.

Modules (Gradle multi-project, root `settings.gradle`: `rfr-api`, `rfr-auth`, `rfr-e2e`; the frontend is a separate npm project):

| Module | Role | Port |
|---|---|---|
| `rfr-auth` | Spring Authorization Server (OAuth 2.1 / OIDC), Thymeleaf login/register pages | 9001 |
| `rfr-api` | GraphQL API, OAuth2 resource server, JPA + Flyway | 8081 (`/graphql`, `/graphiql`) |
| `rfr-gql-client` | React 19 + TS + Vite + Apollo + MUI SPA (finished, written against the fixed schema) | 3001 |
| `rfr-e2e` | JUnit 6 + Playwright Java + Allure 3 (only a placeholder test so far) | — |

Stack: Java 25 (Gradle toolchain), Gradle 9.7.1 wrapper, Spring Boot 4.1.1 (BOM applied from root `build.gradle` to api/auth), MySQL 8.4.

## Commands

```bash
bash localenv.sh                 # MySQL in Docker (root/secret, :3306). WARNING: stops and removes ALL docker containers
bash ports.sh                    # kill whatever listens on 9001/8081/3001

./gradlew :rfr-auth:bootRun      # start auth first — rfr-api fetches JWKS from it
./gradlew :rfr-api:bootRun
./gradlew :rfr-api:generateJava  # regenerate GraphQL model classes (runs automatically on compile)
./gradlew build

./gradlew :rfr-e2e:test
./gradlew :rfr-e2e:test --tests 'io.student.rangiffler.test.fake.SimpleTest'   # single test class/method
./gradlew :rfr-e2e:allureServe   # Allure report (allureReport to just generate)

cd rfr-gql-client && npm i && npm run dev    # also: npm run build (tsc + vite), npm run lint
```

Databases `rangiffler-auth` and `rangiffler-api` are created automatically (`createDatabaseIfNotExist=true`) and migrated by Flyway on startup; `ddl-auto: none`, so schema changes go into new migrations under `src/main/resources/db/migration/<schema>/`.

## Architecture

### Auth flow
- Frontend uses Authorization Code + PKCE with public client `client` (no secret, no refresh token). Login must start from `/oauth2/authorize` (or the frontend Login button); a bare `GET /login` redirects back to the frontend.
- `AccessTokenCustomizer` (rfr-auth) adds `aud: rangiffler-api` and an `authorities` claim (`read`, `write`, from the `authority` table; `FACTOR_*` filtered out) to the **access token only**.
- `rfr-api` validates issuer, signature and audience, maps `authorities` to `GrantedAuthority` without prefix. It rejects `id_token` (401). The current username is the JWT `sub` claim (`@AuthenticationPrincipal Jwt`).
- The RSA signing key is regenerated on every rfr-auth start → restarting auth invalidates all issued tokens.
- `/oauth2/revoke` works for the public client thanks to `PublicClientRevocationAuthentication{Converter,Provider}`; revoked JWTs are still accepted by rfr-api until `exp` (local validation).
- User UUIDs in `rangiffler-auth` and `rangiffler-api` are independent; the only link is username. The API profile is created lazily on first `Query.user`.

### rfr-api (GraphQL)
- Schema `rfr-api/src/main/resources/graphql/query.graphqls` is the contract the frontend is built against — don't change its shape.
- Java GraphQL types (`io.student.rangiffler.model.types.*`) are **generated by DGS Codegen** into `build/generated/sources/dgs-codegen`; don't hand-write them. `typeMapping` in `rfr-api/build.gradle` maps `UserConnection`/`PhotoConnection` to `Page<...>` and `Date` to `LocalDate`. `*Connection` types are not declared in the schema — Spring GraphQL synthesizes them from `Page`/`Slice` returns (IDEA showing them red is expected). If services return `Slice`, change the typeMapping accordingly.
- Security: `POST /graphql` is `permitAll` at the filter level; access is enforced per controller with `@PreAuthorize` — query controllers require `read`, mutation controllers `write`.
- Controller conventions: `@Argument("name")` with explicit names, paging args as `@Nullable Integer` (clients may send explicit `null`). Nested fields (`User.friends`, `Feed.photos`, `Photo.likes`, …) are resolved via `@SchemaMapping` — never call those methods directly.
- Error contract (`GraphQlExceptionResolver`): `ResourceNotFoundException` → `NOT_FOUND`; `FriendshipActionException` and `IllegalArgumentException` → `BAD_REQUEST`; everything else → `INTERNAL_ERROR` without details. Responses are HTTP 200 with `errors[]`; the frontend shows messages only for `BAD_REQUEST`/`NOT_FOUND`. Keep this contract in new services; e2e negative tests assert on `classification` + `message`.
- **Real (DB)**: users, countries, friendship (`UserQueryController`, `UserMutationController`, `CountryQueryController`, `UserServiceImpl`).
- **Mock**: feed, photos, likes, stats (`FeedMockQueryController`, `PhotoMockMutationController`, `FeedMockData` reading `resources/mock/*.json`). Mutations return plausible objects but persist nothing. Tables `photo`, `like`, `photo_like`, `statistic` exist in the migration but are unused — implementing them is the main backend task.
- `V1__schema_init.sql` is written as one monolithic DB; microservices are expected to split it.

### Data-layer patterns to follow
- Friendship is its own aggregate (`FriendshipEntity` + `FriendshipRepository`), **one row per user pair** (`requester`, `addressee`, `PENDING`/`ACCEPTED`); uniqueness of the unordered pair is enforced by DB generated columns `user_low_id`/`user_high_id`. Transition rules live on the entity (`request`, `accept(actor)`, `assertCanDecline(actor)`); `@Version` optimistic lock. Service uses `saveAndFlush`/explicit `flush()` so constraint/lock exceptions are caught inside the service and turned into `FriendshipActionException`.
- Lists of people are fetched in a single paginated JPQL query into the `UserWithStatus` record (`select new ...`), joined with country to avoid N+1; each query exists in with-search and without-search variants and the service picks one. `FriendStatus` is derived from `friendshipStatus` + `isRequester`.
- Pagination must come from a single repository query taking `Pageable` (not from entity collections). Use projections for computed fields like `isOwner`. Use `java.time`, not `java.util.Date`.
- Check object ownership on mutations (editing/deleting someone else's photo, double likes).

### Gotchas
- Spring Boot 4 uses Jackson 3: `tools.jackson.databind.*`, not `com.fasterxml.jackson.databind.*`.
- HQL/JPQL in `@Query` is validated only at application startup (needs DB); `./gradlew build` won't catch query errors.
- Compilation needs `-parameters` (set in root `build.gradle`); builds outside Gradle (e.g. VS Code `bin/main`) fail with `Name for argument of type [...] not specified` unless argument names are explicit.
- `rfr-e2e` runs tests with the AspectJ weaver agent (for Allure steps); JUnit parallel execution is configured but disabled in `rfr-e2e/src/test/resources/junit-platform.properties`.
- Frontend config is in `rfr-gql-client/.env` (`VITE_AUTH_URL`, `VITE_API_URL`, `VITE_CLIENT_ID`, …); access token is stored in `localStorage` under `access_token` (handy for GraphiQL/curl with `Authorization: Bearer ...`).
