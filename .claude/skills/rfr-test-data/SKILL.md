# Тестовые данные rfr-e2e

Данные теста создаёт и удаляет фикстура за `@User TestUser`. Тест сам в БД не пишет.

## Правила

1. **Уникальные данные.** Имена и пароли — случайные (`randomUsername()` / `randomPassword()` в `UserRequest`): тесты делят одни БД (а с включённым параллельным запуском — и время), фиксированное имя столкнётся с чужим тестом или с остатками упавшего прогона. Фиксированное имя — только в пробах `UserExtensionTest`, которым его нужно знать заранее.
2. **Владелец — дерево декораторов.** Корень `UserFixture` в Store, каждый декоратор удаляет то, что создал. Подробности и проверка — skill `rfr-test-review`.
3. **Новая связь — новое значение `Relation`, другое предусловие — новый декоратор.** Для связи через `friendship`: константа в `Relation` (`friendship()` + `attach()`), счётчик в `@User` и `UserRequest` (с проверкой в компактном конструкторе), обёртка `UserWithRelationsFixture` в `UserRequest.fixture()`. Не флаг в `SingleUserFixture` и не ветка в `UserExtension`.
4. **SQL только в объектах строк `data/db`** (`AuthAccount`, `Profile`, `Friendship`, `Friendships`): фикстуры вызывают их `create()` / `delete()` / `exists()`, SQL в фикстуре или тесте нет. Новая таблица со ссылкой на пользователя — правило из `rfr-e2e/CLAUDE.md` про `DELETE_CHILDREN_SQL`.
5. **Профиль API создаётся явно**, вместе с аккаунтом auth (`SingleUserFixture`). Сам API заводит профиль только при первом `Query.user`; без явного профиля связи и проверки в `rangiffler-api` не на кого вешать до логина.
6. **Пул заранее заведённых пользователей — только там, где создать нельзя.** Всё, что фикстура может создать, она создаёт сама. Пул не заводить ради скорости; если он понадобится, тесты его только читают и не меняют.
