# Правила, добавленные в skill rfr-page-objects

Правила выведены из истории работы над `test/profile/ProfileTest` и `test/auth/LoginNegativeTest`, затем обобщены, чтобы применяться не только к странице профиля. В `.claude/skills/rfr-page-objects/SKILL.md` каждое помечено *(добавлено)*.

## Правила (12–15)

| # | Правило | Откуда взялось |
|---|---|---|
| 12 | **Действие, после которого возможен уход со страницы, ждёт свой запрос.** Метод ждёт ответ через `page.waitForResponse(predicate, button::click)`, иначе навигация оборвёт запрос, который ещё выполняется. Запрос узнаётся однозначно (для GraphQL — по `operationName`, URL у всех операций общий). Правило 6 это не нарушает: элементы Playwright ждёт сам, а сеть — нет. Если запрос в каком-то сценарии не уходит (блокирует клиентская валидация), нужен отдельный метод без ожидания. | `reload()` сразу после Save мог оборвать мутацию `UpdateUser`; негативные тесты длины имени упали бы по таймауту, поэтому появился `saveInvalidProfile()` |
| 13 | **Сохранение проверяется после перезагрузки.** Значение в форме сразу после сохранения — состояние страницы, а не данные сервера. | Требование «чтение после reload»; метод `ProfilePage.reload()` |
| 14 | **Проверка должна отличать правильное значение от любого другого.** Сравнивать с точным значением, а не с префиксом, «не пусто» или «элемент есть». | Аватар сравнивается с data URL загруженного файла целиком, а не с префиксом `data:image/` |
| 15 | **Локаторы ленивые.** Элементы, которые появятся позже (уведомления, ошибки валидации), тоже объявляются полями в конструкторе; в методе собирается только локатор, зависящий от параметра. | Вопрос, как правило 3 сочетается с локатором уведомления, которого при создании страницы ещё нет |

## Локаторы

| Правило | Откуда взялось |
|---|---|
| **Элементы и `id` могут повторяться**: закрытые диалоги и порталы остаются в DOM. Искать внутри своей области (`main`, `dialog`, компонент); strict mode violation исправлять сужением области, а не `.first()` / `.nth()`. | Скрытый диалог добавления фото содержит второй `#image__input`: первый прогон загрузил аватар не в тот input |
| **Составное имя — фильтр по точному дочернему элементу.** Не искать по подстроке `hasText`: «user1» найдёт и «user10», «Save» — и «Save draft». Фильтровать через `setHas(<локатор с setExact(true)>)`. | Опции выбора страны: имя складывается из флага и названия («France France»), поэтому опция ищется по `IMG` с точным именем страны |
| **Нет ни имени, ни `id`**: CSS по атрибуту внутри области и комментарий, почему локатор однозначен. | Картинка аватара без `alt`: `main.locator("img:not([alt])")` |

## Организация тестов

| Правило | Откуда взялось |
|---|---|
| Пакет по области приложения (`test/auth`, `test/profile`), негативные сценарии — в отдельном классе `*NegativeTest`. | Задания на `test/profile/ProfileTest` и `test/auth/LoginNegativeTest`; тест неверного пароля перенесён из `LoginTest` |
| Тестовые данные готовятся фикстурами (`@User`), а не через UI, если сам UI-путь не предмет теста. Базового класса теста нет: общие шаги — `private static` метод в классе. | Все тесты профиля на пользователе из `@User`, вход — `login(page, user)` |
| Случайные данные только там, где нужна уникальность (имя пользователя, пароль). Остальные значения — конкретные константы, чтобы падение воспроизводилось. | Требование «страна конкретная, не случайная» (`LOCATION = "Canada"`) |
